Muse Proxy API

A gateway that trades a password for scoped, revocable API keys.

Reading this as an agent? Load /api/agent with your key first — it reports exactly which connections and collections you can reach, and at what level. Also read /llms.txt.

Why this exists

Agents usually need broad credentials to be useful. Muse Proxy inverts that: the account owner stores the password once, chooses which calendars or address books may be touched and whether writes are allowed, then issues a key per agent. A key can be deleted at any time without changing the upstream password.

Two layers of permission

Every request must satisfy both, and a key can only ever be narrower than the connection it uses:

LayerSet byApplies to
Connection ceilingThe account owner, per collectionnone, read or write
Key grantThe account owner, per keyA collection, or every collection the connection allows (*)

Effective access is the lower of the two. Collections default to none, so a new connection exposes nothing until it is deliberately scoped.

Authentication

Authorization: Bearer muse_...

Keys are 256 random bits, shown to the human once, and stored only as a SHA-256 hash. Never pass a key in a query string.

Endpoints

Service catalog

GET /api/agent

Without a key: the available services and where their documentation lives. With a key: additionally the connections and collections that key may reach, each with its effective access, plus any pending notices. Start every session here.

Specification

GET /api/agent/openapi.json
GET /api/agent/<service>/openapi.json

OpenAPI 3.1, generated by the Worker from the same declarations its router uses, so what is published is what this version actually serves.

Notices

GET  /api/agent/notices
POST /api/agent/notices/ack   { "ids": ["..."] }

Notices tell you that something changed: a collection's ceiling was lowered, credentials were rotated, a connection was deleted, or the API version moved. Every response carries the pending count so you do not have to poll:

X-Muse-Api-Version: 2026-09-12
X-Muse-Notices: 2
X-Muse-Notices-Url: /api/agent/notices

When the count is non-zero, fetch the notices and report the ones that affect your work to the human you are acting for. Acknowledge them once you have.

Services

ANY /api/agent/<service>/<connectionId>/<path>

Each service defines its own surface. Currently:

  • caldav — CalDAV and CardDAV, spoken directly.

Refusals tell you what to do

A denied request is a 403 with a body naming the required level, the level you actually have, and the resources you are allowed to use:

{
  "ok": false,
  "apiVersion": "2026-09-12",
  "error": {
    "code": "insufficient_access",
    "message": "This key has read access to 'calendars/me/home' but write is required.",
    "details": {
      "required": "write",
      "effective": "read",
      "resource": "calendars/me/home",
      "permittedResources": ["calendars/me/home"]
    }
  }
}

Reading details.permittedResources is usually enough to fix the request. Keys are in canonical form — for a path-shaped service that means no leading or trailing slash, and the service's own docs show how to address them. Do not retry a refused write unchanged; the human has to widen the grant.

Status codes

CodeMeaning
200 / 207Success, forwarded from the upstream service.
401Missing or expired key.
403The key is valid but not allowed. Read the details.
405Method not supported by this gateway.
502The upstream service could not be reached.

Versioning

The API is date-versioned. Every response carries X-Muse-Api-Version; when it changes you receive an api_version_updated notice linking the changelog.

For people

The admin console is at /user/ — that is where services are connected and scoped, and where keys are minted.
