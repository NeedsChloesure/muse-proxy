API changelog

The API is date-versioned. Every response carries X-Muse-Api-Version. When the deployed version changes, each active API key receives an api_version_updated notice pointing here.

2026-09-13 current

  • admin: GET /api/admin/activity and the console's Activity page were removed. The per-request audit log was an unbounded table on a deployment meant to stay inside the Workers Free plan, and it is not part of the agent API, so no agent-facing surface changes. What a human needs day to day — whether a key is still in use — remains visible per key as its lastUsedAt timestamp.
  • core: keys are deleted, not revoked. DELETE /api/admin/keys/:id removes the key outright — grants and unread notices cascade with it — and a previously revoked key now authenticates exactly like any unknown token. The revoked field is gone from the key object and PATCH body, as is the console's re-enable action. To stop an agent immediately, delete its key and mint a fresh one; a key that passes its own expiry stays listed as expired — with its last-used timestamp — until you delete it. If your tooling relied on revokedAt in admin responses, read active and expiresAt instead.
  • core: notice delivery changed from store-and-catch-up to emit-time fan-out. A notice is written per affected key when it is emitted and is deleted when acknowledged; previously a shared copy was kept and re-delivered when a key was minted or granted the collection afterwards. Agents that poll X-Muse-Notices see no difference in practice — every change to your access still arrives as a notice — but a notice can no longer arrive for a change a key could not have acted on at the time. The ack endpoint is unchanged, and the endpoint now returns pending as the number of unread rows rather than the count of a shared table.

2026-09-12

  • caldav: request bodies are now forwarded for REPORT and PROPFIND, which were previously dropped. This is a fix, not a feature: a calendar-query, calendar-multiget or sync-collection sends its query in the body and could not work without it, and a PROPFIND that named its properties silently degraded into a request for all of them.
  • caldav: a REPORT body names its own targets, so each one is now authorized individually rather than only the path the request was sent to. Two refusals are new: 400 invalid_report when the body cannot be read well enough to know what it references, and 400 invalid_report_href when a reference does not resolve inside the connection. A calendar-multiget that names a collection your key cannot read is refused, where before the upstream server would have answered it.

2026-09-11

  • Initial version.
  • GET /api/agent service catalog, unauthenticated for the service list and capability-reporting with a key.
  • GET /api/agent/openapi.json and per-service specifications, generated from the same declarations the router uses.
  • GET /api/agent/notices and POST /api/agent/notices/ack, plus X-Muse-Notices on every response.
  • caldav service: transparent CalDAV/CardDAV gateway with method and path authorisation, locally answered OPTIONS, and MOVE/COPY destination authorisation.
  • Human-facing admin API under /api/admin and the console at /user/.

Compatibility policy

Within a version, changes are additive. A change that could break existing tooling — a renamed field, a changed default, a new refusal — bumps the version and is announced with a notice, never silently.

Stability notes

  • error.code values are part of the contract; error.message is human-readable prose and may change.
  • details.permittedResources on a 403 is guaranteed, and is the supported way to discover what you can reach without a wildcard grant.
  • Proxied service responses are forwarded from upstream; their bodies are not part of this API's stability promise.
  • Targets named inside a request body — a caldav REPORT href, a MOVE/COPY Destination — are authorized individually. Such a request is refused, and never reaches the upstream server, if any one of them falls outside your grants.
  • A notice is delivered to every key whose grants are affected at the moment the change happens. A key that exists with the relevant grant receives it; a key minted afterwards does not re-receive past notices, because every change to its access from mint time onward is itself announced.
