CalDAV / CardDAV

Service type caldav · all docs

The idea

You speak DAV to this gateway exactly as you would to the server itself. Muse Proxy holds the username and password, injects them upstream, and refuses anything the owner did not permit. You never see the credentials, so a compromised agent cannot leak them.

Addressing

ANY /api/agent/caldav/<connectionId>/<path>

You supply a path, never a URL. The path is relative to the base URL the owner configured, so if the server root is https://cloud.example.com/remote.php/dav/ and the collection is .../calendars/alice/work/, the path is calendars/alice/work/.

Work out what you can reach

Do not guess. Ask the catalog, which reports each collection and your effective level on it:

curl -H "Authorization: Bearer muse_..." https://<host>/api/agent
{
  "data": {
    "connections": [
      {
        "id": "0f1c...",
        "label": "Personal",
        "mount": "/api/agent/caldav/0f1c.../",
        "wildcard": false,
        "resources": [
          { "resourceKey": "calendars/alice/work", "kind": "calendar", "access": "read" },
          { "resourceKey": "calendars/alice/home", "kind": "calendar", "access": "write" },
          { "resourceKey": "addressbooks/alice/people", "kind": "addressbook", "access": "read" }
        ]
      }
    ]
  }
}

Methods

MethodRequires
GET, HEAD, PROPFIND, REPORTread
PUT, POST, DELETE, MKCOL, MKCALENDAR, PROPPATCH, MOVE, COPY, LOCK, UNLOCKwrite
OPTIONSAnswered locally, no access required

Anything else — including ACL — is refused. That is deliberate: privilege changes are not something an agent should do through a scoped key.

Ask before you act

OPTIONS never contacts the server and tells you your own capability set, so it is the cheapest way to avoid a failed write:

curl -i -X OPTIONS -H "Authorization: Bearer muse_..." \
  https://<host>/api/agent/caldav/0f1c.../calendars/alice/home/
HTTP/2 204
allow: OPTIONS, GET, HEAD, PROPFIND, REPORT, PUT, POST, DELETE, ...
x-muse-access: write
dav: 1, 2, 3, calendar-access, addressbook, extended-mkcol

x-muse-access is your effective level on that path. Every proxied response also carries x-muse-access and, when applicable, x-muse-resource.

Discovery and enumeration

Inside a collection you have been granted, everything behaves normally: PROPFIND with Depth: 1, REPORT with calendar-query or calendar-multiget, and so on.

A request that spans collections — the server root, the principal, or a calendar-home — is only permitted when the key has a wildcard grant and the connection allows every collection. Otherwise it is refused, because a Depth: 1 PROPFIND from the root would otherwise reveal the names, URLs and entity tags of calendars you may not read.

Refusals list permittedResources, in the form used everywhere else on this API: the collection path relative to the connection's base URL, without leading or trailing slashes (calendars/alice/work). Use the catalog instead of probing the root.

REPORT

REPORT is how you query rather than list: calendar-query for a time range, calendar-multiget for a specific set of objects, sync-collection for changes since a token. It requires read, and the query itself travels in the request body, which is forwarded intact.

Unlike every other method, a REPORT body names its own targets. A calendar-multiget lists <D:href> elements and the server resolves each of them independently, so the gateway authorizes every href as well as the path you sent the request to. The practical consequence: a href that resolves to a collection your key cannot read is refused, even though the request URL itself was allowed.

curl -X REPORT \
  -H "Authorization: Bearer muse_..." \
  -H "Depth: 1" \
  -H "Content-Type: application/xml; charset=utf-8" \
  --data-binary @multiget.xml \
  https://<host>/api/agent/caldav/0f1c.../calendars/alice/work/

where multiget.xml asks for objects in that same calendar:

<?xml version="1.0" encoding="utf-8"?>
<C:calendar-multiget xmlns:D="DAV:" xmlns:C="urn:ietf:params:xml:ns:caldav">
  <D:prop><D:getetag/><C:calendar-data/></D:prop>
  <D:href>/calendars/alice/work/a.ics</D:href>
</C:calendar-multiget>

Hrefs may be written in whichever form you naturally hold them: relative to the collection (a.ics), as the collection path, as an absolute URL on the connection's origin, or as a gateway path. Anything that does not resolve inside this connection — another origin, another connection — is refused rather than guessed at, since authorizing one resource while the server acted on another is the failure this check exists to prevent. Entity references are not accepted either: they cannot appear in a real href, and a parser that expands them differently from the server's would be a way to name a target the check never saw.

Common operations

List events in a collection

curl -X PROPFIND -H "Depth: 1" -H "Authorization: Bearer muse_..." \
  https://<host>/api/agent/caldav/0f1c.../calendars/alice/work/

Create or replace an event

Requires write. The path ends in the object's filename, usually its UID plus .ics.

curl -X PUT \
  -H "Authorization: Bearer muse_..." \
  -H "Content-Type: text/calendar; charset=utf-8" \
  -H "If-None-Match: *" \
  --data-binary @event.ics \
  https://<host>/api/agent/caldav/0f1c.../calendars/alice/work/<uid>.ics

Move or copy

Both ends are authorized independently: you need write on the source and on the destination. The Destination header is accepted in any of three forms — an upstream path (/calendars/alice/home/x.ics), a gateway path (/api/agent/caldav/<connectionId>/calendars/alice/home/x.ics), or an absolute URL on the connection's origin. Anything outside this connection is refused.

curl -X MOVE \
  -H "Authorization: Bearer muse_..." \
  -H "Destination: /api/agent/caldav/0f1c.../calendars/alice/home/x.ics" \
  https://<host>/api/agent/caldav/0f1c.../calendars/alice/work/x.ics

Redirects

The gateway never follows a redirect on your behalf: the decision to allow a request was made for the collection you asked for, and silently following a Location would re-send that request somewhere the decision does not cover. A 3xx is passed back unchanged, with a Location that stays inside this connection rewritten into gateway coordinates so you can follow it yourself. A Location pointing at any other origin is dropped, because the request carries credentials.

Failure modes worth knowing

ResponseMeaning and what to do
403 no_grantYour key has no grant on this connection at all. The human must grant it.
403 insufficient_accessYou have the wrong level. Read permittedResources; a write needs the owner to widen the grant.
403 on a root-level requestEnumeration across collections needs a wildcard grant. Use GET /api/agent.
401 with a JSON body and no X-Muse-AccessThe gateway refused your key: revoked, expired or mistyped. Do not keep retrying.
401 or 403 carrying X-Muse-AccessForwarded from the upstream server: the human's stored password was refused there. Tell the human; do not attempt to fix credentials yourself.
502The upstream server could not be reached. Tell the human; this is not something you can retry your way out of.
409 / 412Forwarded from upstream: a real DAV precondition failure. Re-read the resource and retry.
400 invalid_reportA REPORT body the gateway could not read: malformed XML, or an href with no readable target. Send well-formed XML with plain paths.
400 invalid_report_hrefA REPORT named a resource that is not inside this connection. Only this connection's own server can be addressed.

When a write is refused, the correct next step is to tell the human what you were trying to do and why it needs a wider grant — not to look for another route. The scoping is the feature.

Notices you may receive

grant_downgraded, resource_removed, connection_deleted and credentials_changed all concern this service. If you cached collection paths or assumed write access, re-read GET /api/agent after receiving one.
